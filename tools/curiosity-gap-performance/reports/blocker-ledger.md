## SEAM PROPOSAL (§48) — one design, deliberately serving both R&D lanes

| | |
|---|---|
| **SEAM NEEDED** | **YES** — for any future lane that wants to execute real production logic rather than model it. |
| **AFFECTED FILES** | `supabase/functions/scan-identify/index.ts` (the `Deno.serve` handler), `supabase/functions/scan-identify/scanCommerceRouter.ts` (`getFastCommerceResults`, `getScanCommerceResults`) |
| **CURRENT COUPLING** | The handler reads `Deno.env` inline, constructs its own Supabase clients, and calls providers directly. The commerce router receives a query and reaches the network itself. Nothing accepts an injected transport, clock or env. |
| **PROPOSED PURE BOUNDARY** | A single `CommerceRuntime` parameter object — `{ fetchImpl, now, envGet, providers }` — threaded through `getFastCommerceResults` / `getScanCommerceResults` with **defaults that reproduce today's behaviour exactly**. No call site changes; no new module; no dependency injection framework. The existing `envGet` parameter on `isCommerceFunnelEnabled` (`commerceFunnelConfig.ts:109`) is already exactly this pattern, so the seam extends a convention the codebase has rather than importing a new one. |
| **MATCH QUALITY LAB ALSO BENEFITS** | **YES — and this is the reason for one proposal instead of two.** A quality lane needs to run real query construction and real ranking against recorded provider responses; a performance lane needs to run the real fan-out against a synthetic clock. Both are the same seam: injectable providers plus an injectable clock. Two competing extraction designs would be strictly worse than one. |
| **ZERO-BEHAVIOUR TEST PLAN** | 1. Snapshot the current `deno test supabase/functions/scan-identify/` suite (314 passing at the Build 34 audit). 2. Land the parameter with defaults; the suite must pass unchanged with **zero test edits**. 3. Add a parity test asserting that omitting the runtime produces byte-identical behaviour to the current call. 4. Run the repo's own `scripts/generate-edge-function-manifest.js` and the edge-parity gate, which will react to the changed hash. 5. Negative control: break one default and confirm the parity test fails. |
| **RISK** | **MEDIUM.** It touches the live commerce path. Mitigated by defaults-only semantics and by the manifest/parity gates the repo already enforces. |
| **OVERLAP WITH MATCH QUALITY LAB** | Complete, by design. This proposal should be reviewed **once**, jointly, not twice. |
| **RECOMMENDED FUTURE PR** | A standalone `chore(scan-identify): inject commerce runtime (defaults preserve behaviour)` PR, reviewed on its zero-behaviour argument alone and merged **before** either lab attempts L1A. |
| **AUTHORIZATION** | **Owner decides.** This lane did not write it, did not prototype it, and did not modify production to enable it. |
