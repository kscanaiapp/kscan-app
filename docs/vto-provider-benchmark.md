## 3. The finding that determined this phase: provider access blocked

An empirical, low-cost probe was run against the **live** endpoint on
2026-08-30 (staging project `yzqjvdfgefveprobvvyw`), using the already-live
`RAPIDAPI_KEY` secret, to verify the real request/response contract before
writing the adapter (the vendor's own docs do not fully specify the async
polling endpoint — that had to be found separately; see the reference list in
§1).

**Method:** a temporary diagnostic Edge Function (`vto-provider-diag`) was
deployed to staging, invoked once with two small **synthetic, non-personal**
test images (solid-color PNGs — not a photo of any real person; see §11 on why
no real person photo was used), then immediately neutralized (redeployed as an
inert 410 stub — this MCP surface has no `delete_edge_function` tool, so a stub
is the safest available cleanup; **the owner should remove this function slug
from the project**).

**Result:**
```
HTTP 403
{"message":"You are not subscribed to this API."}
```

**What this proves:**
- The key **authenticates** — RapidAPI's gateway recognized it as a valid
  account key (a bad/garbled key produces a different, generic 401 from
  RapidAPI's edge, not a per-API subscription message).
- The host, path, and header format used by the existing (rejected)
  `tryon-clothes-pro` function are **correct** for reaching this listing.
- The account behind that key has **never purchased/activated a subscription**
  to this specific marketplace listing — a separate action from having a
  working RapidAPI account key. Other listings the codebase already uses
  (`nike-shoe-details`, `kickscrew-sneaker-description`) work because *those*
  subscriptions exist; this one does not.

**What this means for the prior `tryon-clothes-pro` function:** it was
correctly classified `REJECTED` in Foundation 01 for governance reasons
(no auth, no K+, no sanitation, no validation). This phase adds a harder
fact: **it could never have produced a real image even if none of that were
fixed**, because the account was never subscribed to the API it calls. It also
sends `person_image`/`top_garment` as URL-encoded strings, not the
`multipart/form-data` files the real contract requires — a second,
independent reason it would have failed even with a subscription.

**BLOCKER, not a defect.** Subscribing to a new marketplace API — even a
metered, pay-per-call one — is an account/billing action on the RapidAPI
dashboard. This session did not attempt it and will not without the user
doing it directly, consistent with the standing rule against creating
accounts or making new commercial commitments without explicit permission.

## 8. Category verdicts

All categories: **NOT YET** — no evidence exists for any category with any
provider.

One category-shaped finding **is** available from the documented contract
alone, independent of live testing, and is worth recording now:

- **`dress` / `full_body`:** AILabTools' `top_garment` parameter is
  **required** and there is no `full_body`/dress parameter at all. Today's
  default `supportedCategories` (`top`, `outerwear`, `blazer`, `dress`)
  includes `dress`, which this specific vendor's contract cannot serve
  correctly. `aiLabToolsProvider.ts` refuses `full_body` (and `bottom`, which
  has the same required-`top_garment` problem) with `unsupported_category`
  rather than sending a malformed request — see `unsupportedSlotReason()` and
  its test coverage. **If this vendor becomes the shipping provider, `dress`
  must be removed from `supportedCategories` in `app_config.vto_generation`
  until a vendor with an explicit one-piece/full-body path is used** (FASHN's
  documented auto-detection of "one-pieces" is the strongest public candidate
  for that gap).

## 13. K Scan privacy path (as built, real path once unblocked)

```
user's photo (photo library, explicit selection)
        ↓
prepareImageForPrivacyUpload  -- re-encodes, strips EXIF (the ONLY sanitation claim)
        ↓
vto-generate (staging, authenticated)  -- validates JWT, account, flag, K+, eligibility
        ↓
aiLabToolsProvider.ts  -- fetches the garment image server-side, builds multipart form
        ↓
AILabTools (via RapidAPI)  -- receives person image + garment image; NO K Scan identity
        ↓
poll → image_url (their CDN, 24h TTL)
        ↓
vto-generate fetches that URL server-side, re-encodes as a data URI
        ↓
validateVtoResultMedia  -- structural check only
        ↓
returned inline to the client; NOTHING written to K Scan storage at any step
```

What leaves the device: the sanitized (metadata-stripped) photo, as base64,
over TLS, to `vto-generate`. What K Scan's server sees: that same image,
in memory, for the duration of one request. What the provider sees: that
same image plus the garment image; no user id, no session, no K Scan
identity of any kind (the adapter interface has no such field). What is
retained: nothing by K Scan; up to 24h by AILabTools per §12. What is logged:
the same closed allowlist as Foundation 01 — no image, no URL, no
credential.

## 14. Background / lifecycle

**No provider-driven changes were needed or made.** The Foundation 01
stale-result rule (monotonic generation token + actor epoch, both checked
before any result is applied) already covers a slow real provider exactly as
it covers the mock's simulated latency — nothing about AILabTools' actual
behavior was observed to require a durable job/rehydration mechanism, because
no real generation ever ran long enough to test backgrounding against it.
**This is deferred, not solved:** if a real generation is later found to run
past what a foregrounded app session tolerates, that finding — not this
report — should decide whether a durable job id is worth adding.

## 15. Failures (real, observed)

One real failure mode was observed live: `403 subscription-gate`, mapped by
the adapter to `provider_unavailable` (§3, tested in
`aiLabToolsProvider.test.ts`). Every other failure path in the adapter
(`429`, `5xx`, non-zero `error_code`, moderation-flagged `error_msg`, a
missing `task_id`, a stuck poll, an oversized/malformed result) is built from
the documented contract and unit-tested against synthetic responses, **not
observed from the live vendor**, because no request ever got past the
subscription gate to produce one.

## 21. Final program verdict
