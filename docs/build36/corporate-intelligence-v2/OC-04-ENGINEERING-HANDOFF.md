# OC-04 PostgreSQL execution hardening

Engineering verdict: **PARTIAL for future runtime integration; all 21 isolated real-PostgreSQL scenarios PASS.** Three clean-checkout governance assertions fail because the concurrent canonical authority tip is newer than the requested OC-03 base. The retained global writer fence also has measurable cross-account serialization and a reproducible row-first legacy deadlock risk. It must remain until all relevant writers share a reviewed lock protocol. This is not production certification or activation approval.

No release branch, frontend, Edge Function entrypoint, deployment, live database, environment setting, auth/storage policy or protected baseline was changed. No new schema or production migration is proposed in OC-04; the existing proposed OC-02/OC-03 SQL is loaded only into disposable databases.

## Repairs and transaction contract

1. **Opposing reserve/status lock order:** real PostgreSQL detected `40P01` when reserve held ledger then waited for policy/profile while status held policy/profile then waited for ledger. Reserve now acquires policy/profile before ledger, matching status/reconciliation. The actor advisory lock alone did not serialize these read/recovery paths. The deterministic reproduction passes after repair.
2. **Removed Watch restoration:** the existing creation RPC ignores tombstones, allowing an older approved save to recreate a later removed Watch. The isolated save adapter now refuses creation when a tombstone exists for that actor and canonical URL, under the retained writer fence. This is deliberately conservative: even a tombstone predating the proposal blocks this save path. Restoration needs a separately designed approval binding; this change adds no restoration capability. Existing active identical Watches remain no-ops; paused or changed-intent Watches are refused.
3. **Explicit transaction driver:** `createTransactionDatabase` accepts a structural pool port, with no credential reader, network provider or retry loop. One physical checkout owns BEGIN, all callback SQL, and COMMIT/ROLLBACK. Only an acknowledged COMMIT or ROLLBACK returns a reusable connection. Acquisition timeout discards a late checkout. A whole-transaction deadline discards the socket and fences escaped/late SQL; transaction-local server statement and idle timeouts bound server work. Unknown COMMIT is reported as uncertain and never replayed. Metadata-only telemetry cannot change the result. The integration agent still chooses the actual pool/client adapter and infrastructure limits.

Only `save_watchlist` with `just_watching` and null target price remains executable. OC-02 approvals still require the exact OC-03 binding and authenticated principal; `canClaimCompletion` remains the success authority. CI-05 Option B and default-OFF behavior remain covered by existing regressions.

## Lock decision and narrow follow-up proposal

Retain `LOCK TABLE public.user_commerce_watches IN SHARE ROW EXCLUSIVE MODE`.

The alternative experiment takes an actor advisory lock and `FOR UPDATE` on the absent Watch row. The unchanged legacy RPC creates a `buy_under` Watch through another physical connection; its unique-conflict path then permits the candidate save RPC to overwrite that intent. The experiment verifies the overwrite and rolls it back. Actor locks, absent-row locks and the existing uniqueness constraint therefore do not establish compatibility with legacy writers. An optimistic insert-only redesign would also need a reviewed answer for legacy intent/removal races and the account-wide Watch ceiling; it was not substituted without that proof.

A legacy transaction that locks a Watch row first and later requests a table write lock can deadlock with the executor's table-first fence. The adversarial test observes one PostgreSQL victim and checks that any claimed completion agrees with the resulting Watch. This is a retained reliability/capacity risk, not a reason to drop the correctness fence. The measured batches are too small to estimate production deadlock probability.

Follow-up owned by the integration agent: inventory create/update/pause/delete, trigger, background and direct service writers; select one transaction-scoped actor lock namespace and universal order before account/product/Watch row locks; change every relevant writer in one reviewed patch; ensure the account-wide count check and insert are serialized; retest same/multiple-account, absent-row, intent, removal, row-first, limit and recovery races; only then evaluate replacing the global lock. No active legacy RPC or customer entrypoint is edited here. Direct writes that bypass the protocol would invalidate that replacement.

The workload records 0/24 timeout or deadlock failures, 8/24 `already_watched` no-ops, pool high-water 8 and no sampled checkout queue. Each batch adds 8 ledger and 24 audit rows; five status polls add zero audit rows. All three account-deletion probes cascade their ledgers; all three runtime DELETE probes are denied. The separate forced scenarios produce one legacy row-first deadlock and one `55P03` table-lock timeout; transaction and acquisition deadline cases also pass. Across the entire run the largest sampled checkout queue is one, in the intentional pool-exhaustion case. The six duplicate execution requests produce one RPC call and one durable completion event. Actual COMMIT acknowledgement loss produces one packet drop and one mutation call, including retry.

Lock wait samples poll `pg_locks.waitstart` every 5 ms, group each wait episode and retain its observed maximum. Short waits can be missed; observed waits are lower bounds. Table-lock statement durations include transport and other work and are reported separately as elapsed upper bounds. Workload errors are separated from deliberately injected deadline/deadlock/failure cases. Different batches can be faster or slower because of cache/host scheduling; this is not a controlled throughput benchmark.

Each batch measures ledger/audit/Watch growth, five status polls, service-role DELETE denial and privileged synthetic account-deletion cascade. Ledger has one row per action, audit has transition rows, and polling does not append transition audit. Runtime automatic archival is **not implemented**: ledger evidence intentionally survives OC-02 proposal cleanup; a retention/purge policy with privacy, recovery and audit requirements is an integration dependency. Account deletion cascade is tested only in the disposable fixture and is not a substitute for an approved retention policy.
