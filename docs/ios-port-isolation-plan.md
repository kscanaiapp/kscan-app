# iOS Port Isolation Plan — K Scan AI

* Created: 2026-06-14
* Android baseline branch: release/android-1.0.0
* Android baseline commit: 7cee958
* Android versionName/versionCode: 1.0.0 / 5
* Android Play status: Internal Testing uploaded; waiting for tester feedback
* Freshness rule: If Android tester feedback changes the release branch, update this plan before creating an iOS branch.

---

## 1. Purpose

This document defines the isolation boundary between the frozen Android 1.0.0 release and future iOS port work. Its purpose is to ensure that iOS planning, branching, build setup, and App Store submission do not alter, pollute, or destabilize the Android release candidate currently in Google Play Internal Testing.

**This document does not authorize iOS work.** No iOS branch should be created, no `expo prebuild` should be run, and no `ios/` directory should be generated until the owner explicitly authorizes iOS work after reviewing Android tester feedback.

---

## 2. When iOS Work May Begin

iOS work must not begin until **at least one** of the following conditions is met:

| Condition | Status |
|---|---|
| Android tester feedback reviewed and approved by owner | PENDING — not yet received |
| Owner explicitly authorizes iOS work in writing regardless of feedback | NOT YET AUTHORIZED |

Until one of these conditions is satisfied:

* Do not create `feature/ios-port`.
* Do not run `expo prebuild`.
* Do not run `pod install`.
* Do not generate an `ios/` directory.
* Do not modify `app.json`, `eas.json`, or any shared config file for iOS purposes.
* Do not create Apple developer credentials, bundle IDs, or App Store Connect entries for submission.

---

## 3. Recommended Branch Creation

When the owner authorizes iOS work, create the iOS branch from `release/android-1.0.0` to ensure all release-hardening commits are included:

```bash
git checkout release/android-1.0.0
git checkout -b feature/ios-port
```

**Do not run this command in this task.**

The owner should also decide, at branch-creation time, whether to branch from:

* `release/android-1.0.0` — recommended; includes all release-hardening commits
* `main` or `master` — only if release commits have already been merged back
* A dedicated post-Android stable branch — if one is created after Android production approval

Do not branch from a feature branch (e.g., `feature/purple-gold-electric-theme`) as that branch is missing 7 release-only commits present on `release/android-1.0.0`.

## 4. Files Allowed During iOS Work

The following files may be created or modified on the iOS branch after owner authorization:

* `ios/` — generated by `expo prebuild`, intentional only on iOS branch
* iOS-specific `app.json` fields (`expo.ios.*`) — within the shared `app.json`, iOS additions only; see Section 7
* EAS iOS build profile and iOS-specific config — after review
* Apple bundle identifier documentation
* Apple privacy manifest documentation (`PrivacyInfo.xcprivacy`)
* TestFlight submission documentation
* iOS screenshots and App Store assets
* App Store review notes and metadata
* iOS permission strings (`NSCameraUsageDescription`, etc.)
* iOS-specific QA artifacts under `qa/`

---

## 5. Files Protected From iOS Work

The following files must not be modified during iOS work under any circumstances without explicit owner authorization and a separate documented review:

**Android source files:**
* `android/` (entire directory)
* `android/app/build.gradle`
* `android/app/src/main/AndroidManifest.xml`
* Android signing config and keystore references
* Android `versionCode` (must remain at 5 unless an Android hotfix is explicitly authorized)
* Google Play metadata and Data Safety responses
* Android AAB artifacts (`qa/aab-final/app-production-beta1.aab`)

**Release branch history:**
* `release/android-1.0.0` branch history must not be rebased, amended, or force-pushed

---

## 6. Shared Files Requiring Special Review

Every shared file edited on the iOS branch must be classified before the change is committed:

| Classification | Required action |
|---|---|
| iOS-only | Document classification in PR description; proceed |
| Android-impacting | Owner must review and approve before commit |
| Shared runtime | Owner must review; consider whether change belongs on Android release branch too |
| Unknown / needs review | Do not commit until reviewed |

Shared files that require this classification review:

* `app.json`
* `package.json`
* `package-lock.json` / `yarn.lock` / `pnpm-lock.yaml` / `bun.lockb`
* `eas.json`
* `babel.config.js`
* `metro.config.js`
* `tsconfig.json`
* `index.js`
* `app/_layout.tsx`
* Shared route files
* `constants/`
* `assets/`
* Shared theme files
* Shared auth files
* Shared Supabase client/config files

---

## 7. app.json Multi-Platform Boundary

When `app.json` is eventually modified on the iOS branch, the following rules apply:

* **Zero modifications** are permitted to the existing `expo.android` block, including:
  * `package` (`com.kscanai.app`)
  * `versionCode` (5)
  * `permissions`
  * `splash`
  * `icon` and `adaptiveIcon`
  * `intentFilters`
  * Any Android plugin configuration

* iOS additions must be isolated to the `expo.ios` block wherever possible.

* If a change must be made outside platform-specific blocks (e.g., top-level `name`, `version`, `plugins`), it must be classified and owner-approved before commit.

* After any `app.json` change on the iOS branch, run a diff against `release/android-1.0.0`'s `app.json` and document what changed in the PR description.

---

## 8. Shared Asset Boundary

* Do not overwrite shared assets to solve iOS-only rendering issues.
* If an asset must be optimized for iOS, add an iOS-specific variant instead of replacing the shared Android asset.
* Assets to review before any iOS-branch modification:
  * `assets/` (all icons, splash screens, fonts, images)
  * `constants/` (theme colors, typography, spacing, brand values)
  * Shared icon files
  * Shared splash/adaptive splash assets
* Any shared asset change must be classified using the table in Section 6.
* Replacing a shared icon or splash image that is used by the current Android AAB is an Android-impacting change and requires owner authorization.

## 9. Apple Privacy/Legal Review Warning

Before any iOS App Store submission, the privacy policy and App Store metadata must be reviewed against the following known risks. **Do not rewrite the privacy policy in this task or during iOS branch setup.**

Items requiring legal/product review before iOS submission:

| Claim | Risk |
|---|---|
| "13+" or teen/minor age language | Android posture is 18+; App Store age rating must match actual content policy |
| On-device privacy filtering / face blurring claims | Must match actual implemented behavior at submission time |
| Advertising / attribution / affiliate tracking language | Must reflect actual SDK usage and ATT (App Tracking Transparency) implementation |
| App Tracking Transparency language | ATT prompt required if any cross-app tracking occurs; verify implementation |
| Account deletion wording | Must match the actual in-app deletion flow and Play/App Store deletion requirements |
| AI provider disclosure language | Must accurately reflect current AI provider(s) and model usage |
| Smart glasses, AR, voice, checkout, or roadmap-only claims | Remove or defer if not implemented in 1.0.0 |

The owner must schedule a legal/product review of the privacy policy and App Store metadata before submission. Do not submit to App Store Review with unreviewed privacy claims.

## 10. Build and Submission Boundaries

| Action | Allowed during iOS planning? | Allowed during iOS build work? |
|---|---|---|
| `expo prebuild` | NO | YES, on iOS branch only |
| `pod install` | NO | YES, on iOS branch only |
| `eas build --platform ios` | NO | YES, after owner authorization |
| `eas submit --platform ios` | NO | YES, after TestFlight validation |
| `eas build --platform android` | NO — never on release branch | Only if hotfix authorized |
| Modify Android build.gradle | NO | NO — Android-protected |
| Modify eas.json Android profile | NO | Owner review required |
| Deploy Supabase functions | NO | Only if iOS-specific function required, separate authorization |
| Run database migrations | NO | Only if iOS-specific schema change required, separate authorization |

## 12. First iOS Planning Tasks (After Authorization)

When the owner authorizes iOS work, the recommended first planning tasks are:

1. Confirm the iOS bundle ID strategy: use `com.kscanai.app` on iOS or a separate ID.
2. Review Apple developer team enrollment and provisioning profile setup.
3. Decide on EAS build profile for iOS (managed vs. bare workflow).
4. Document Apple privacy manifest requirements for camera, photo library, and any networking APIs.
5. Schedule legal/product review of privacy policy against the risks documented in Section 9.
6. Create `feature/ios-port` from `release/android-1.0.0`.
7. Run `expo prebuild --platform ios` on the iOS branch.
8. Review generated `ios/` for any Android-impacting side effects.
9. Set up TestFlight for internal testing.
10. Define iOS QA smoke test checklist parallel to the existing Android V6 runtime smoke.

**None of these tasks should begin until the owner explicitly authorizes iOS work.**
