## Method

- **Unindexed foreign keys.** Postgres enforces `ON DELETE CASCADE / SET NULL`
  with a per-row trigger on the parent. Without an index that *leads* with the
  foreign key, each deleted parent row scans the whole child. The deciding
  question was therefore "which parent is deleted in bulk on a customer
  lifecycle path?", not "which FK lacks an index". For each key the RI query
  shape (`UPDATE/DELETE ... WHERE fk = $1`) was `EXPLAIN`ed on staging with
  sequential scans disabled (read-only). Staging statistics corroborate the
  mechanism: `outfit_decision_option_items` recorded 6,610 sequential scans
  against 6,571 `saved_scans` deletions, while the already-indexed control
  `look_items.source_saved_scan_id` recorded 6,572 index scans.
- **RLS init-plan.** All 102 policies were read from `pg_policies`. Every one
  is the plain owner predicate `auth.uid() = <owner column>` (inside `EXISTS`
  for child tables), and the owner column is indexed on every table. The
  `(select auth.uid())` rewrite is semantically identical but edits
  authorization text, so it is not done without evidence of launch risk.
- **Unused indexes.** Staging traffic cannot prove an index is useless. Each
  index was checked for FK support and size; none was dropped.
- **Multiple permissive policies.** Each policy set was read and its OR
  semantics compared with the intended authorization. A rolled-back
  impersonation probe confirmed `anon`/`authenticated` cannot write
  `app_config` (the reconciler kill switch lives there).
